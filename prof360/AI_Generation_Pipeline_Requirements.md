## 1. Overview

### 1.1 Purpose

This document specifies the data and AI requirements for three Python batch jobs that generate structured intelligence content for the Underwriting Intelligence platform. The jobs read pre-processed SEC filing and Alpha Vantage news data from Azure SQL, call the SecureGPT REST API to generate structured insights and questions, and write results back to Azure SQL for consumption by the BFF layer.

### 1.2 Scope

This document covers **data and AI requirements only**. Deployment infrastructure (OpenShift CronJob configuration, container specs, scheduling) is out of scope and covered in the infrastructure specification.

### 1.3 Three Jobs Covered

| Job | Description |
|-----|-------------|
| **Job 1** | Key Insights Generation — high-level executive summary cards per company |
| **Job 2** | Strategic & Risk Insights Generation — categorized risk intelligence with reasoning |
| **Job 3** | Follow-Up Questions Generation — broker questions grounded in identified risks |

### 1.4 End-to-End Data Flow

All three jobs follow the same pipeline pattern:

```
Azure SQL (input tables)
  ├── sec_filings     { company_id, filing_type, section, body, period_date }
  └── av_news         { company_id, headline, summary, sentiment_label, published_at }
           │
           ▼  Python job: read → assemble prompt → call SecureGPT REST API
           │
  SecureGPT REST API  POST /v1/chat/completions
           │
           ▼  parse JSON response → validate fields → write
           │
Azure SQL (output tables)
  ├── company_insights              (Job 1)
  ├── company_risk_insights         (Job 2)
  ├── company_followup_questions    (Job 3)
  └── ai_generation_log             (all three jobs)
```

### 1.5 Execution Order

Jobs must run in the following order each batch cycle. Job 3 depends on Job 2 output.

1. **Job 1** — Key Insights Generation *(no upstream dependency)*
2. **Job 2** — Strategic & Risk Insights Generation *(no upstream dependency, runs in parallel with Job 1)*
3. **Job 3** — Follow-Up Questions Generation *(depends on Job 2 completing successfully)*
   - Reads `company_risk_insights` generated by Job 2 to align questions with identified risks

### 1.6 Shared Requirements (All Three Jobs)

- Each job processes all active companies in the `companies` table sequentially.
- For each company, the previous batch's output rows are **deleted and replaced** (full replace per `company_id` per `batch_date`). No row accumulation.
- Each SecureGPT call is logged to `ai_generation_log` regardless of success or failure.
- Malformed or unparseable JSON responses are retried **once** (same prompt). If retry also fails, the company is skipped and an error is logged. The job continues to the next company.
- All prompt templates are stored as **versioned text files**. The `prompt_version` string is logged with every call.
- API key for SecureGPT is read from environment variable `SECUREGPT_API_KEY`. Never hardcoded.
- Azure SQL connection string is read from environment variable `AZURE_SQL_CONN_STR`. Never hardcoded.

## 2. Input Data

### 2.1 SEC Filings Table — `sec_filings`

Contains structured SEC filing content already ingested and parsed. Each row represents one section of one filing for one company.

| Field | Type | Required | Description / Constraints |
|-------|------|----------|---------------------------|
| `company_id` | int | Yes | FK to companies table |
| `filing_type` | varchar(20) | Yes | 10-K, 10-Q, 8-K, DEF 14A |
| `section` | varchar(100) | Yes | e.g. MD&A, Risk Factors, Item 1.01, Governance |
| `body` | nvarchar(max) | Yes | Cleaned plain text of the section |
| `period_date` | date | Yes | Period end date of the filing |
| `filed_at` | datetime | Yes | SEC filing submission timestamp |

**Query pattern** — each job selects the most recent filing per `filing_type` per company:

```sql
SELECT filing_type, section, body, period_date
FROM sec_filings sf
WHERE company_id = @company_id
  AND filed_at = (
    SELECT MAX(filed_at) FROM sec_filings
    WHERE company_id = @company_id AND filing_type = sf.filing_type
  )
ORDER BY filing_type, section
```

### 2.2 Alpha Vantage News Table — `av_news`

Contains news articles and sentiment scores ingested from Alpha Vantage, one row per article per company.

| Field | Type | Required | Description / Constraints |
|-------|------|----------|---------------------------|
| `company_id` | int | Yes | FK to companies table |
| `headline` | nvarchar(500) | Yes | Article headline |
| `summary` | nvarchar(max) | Yes | Article summary or lead paragraph |
| `sentiment_label` | varchar(20) | Yes | bullish / bearish / neutral |
| `sentiment_score` | decimal(5,4) | Yes | Score from 0 to 1 |
| `published_at` | datetime | Yes | Article publication timestamp |
| `source` | varchar(200) | No | Publisher name |
| `url` | varchar(500) | No | Source URL — included in `source_json` citations |

**Query pattern** — each job selects news from the last 30 days, ordered by recency:

```sql
SELECT headline, summary, sentiment_label, sentiment_score, published_at, source, url
FROM av_news
WHERE company_id = @company_id
  AND published_at >= DATEADD(day, -30, GETUTCDATE())
ORDER BY published_at DESC
```

## 3. Job 1 — Key Insights Generation

**Output table:** `company_insights`

### 3.1 Purpose

Generate 8–10 Key Insight cards per company that appear at the top of the Company Detail page. Each card is a concise executive-level signal — either a risk flag or a positive indicator — derived from SEC filings and recent news. These are intentionally higher-level and distinct from the detailed Strategic & Risk Insights (Job 2).

### 3.2 Input Assembly

For each company, assemble the following context before calling SecureGPT:

- **SEC filings:** all sections from the most recent 10-K and 10-Q (MD&A, Risk Factors). 8-K material events from the last 90 days.
- **Alpha Vantage news:** all articles from the last 30 days, formatted as: `[sentiment_label] headline — summary`
- **Truncation rule:** if total assembled text exceeds 80,000 characters, truncate 10-K/10-Q body text (keep first 60,000 chars) but always include 8-K events and news in full.

### 3.3 Prompt Requirements

The prompt must instruct SecureGPT to:

- Return **only valid JSON**. No preamble, no markdown fences, no explanation.
- Return an array of **8–10** insight objects.
- Use only information present in the provided source text. Do not add external knowledge.
- Assign `severity` using the following rules:
  - `red` — material risk, regulatory action, significant financial deterioration, or active litigation
  - `yellow` — emerging risk, elevated uncertainty, or trend requiring monitoring
  - `green` — positive indicator, strong position, or improving trend

### 3.4 Required Output Schema

SecureGPT must return a JSON array where each element conforms to:

| Field | Type | Required | Constraints |
|-------|------|----------|-------------|
| `insight_type` | string | Yes | Short slug identifying the insight theme, e.g. `cre_exposure`, `nim_pressure`, `capital_position` |
| `severity` | string | Yes | Exactly one of: `red`, `yellow`, `green` |
| `title` | string | Yes | Max 60 characters. Concise headline. No trailing period. |
| `summary_text` | string | Yes | 2–3 sentences. Specific figures and dates from source. No generic statements. |

**Example valid output:**
```json
{
  "insights": [
    {
      "insight_type": "leverage_rising",
      "severity": "red",
      "title": "Leverage up, cash still modest",
      "summary_text": "Debt rose to $16.5B in Q1 2026 while cash stayed near $0.5B, with interest expense also moving higher. Stockholders' deficit widened to $4.1B after $3.3B of FY2025 repurchases."
    }
  ]
}
```

### 3.5 Validation Rules (before DB write)

- `severity` must be exactly `red`, `yellow`, or `green`. Reject any other value.
- `title` must not be empty and must be ≤ 60 characters.
- `summary_text` must not be empty.
- `insight_type` must not be empty.
- Array must contain between 1 and 15 elements. Reject if empty or > 15.
- Any insight object failing validation is **dropped individually**. Remaining valid objects are written.
- If zero valid objects remain after validation, the company is skipped and logged as `parse_success = 0`.

### 3.6 Output Table — `company_insights`

| Column | Type | Key | Notes |
|--------|------|-----|-------|
| `insight_id` | int identity | PK | Auto-generated |
| `company_id` | int | FK | FK to companies |
| `insight_type` | varchar(100) | | From SecureGPT output |
| `severity` | varchar(10) | | `red` / `yellow` / `green` — validated before write |
| `title` | varchar(200) | | From SecureGPT output |
| `summary_text` | nvarchar(max) | | From SecureGPT output |
| `batch_date` | date | | Date of the batch run (UTC) |

**Write strategy:**
```sql
DELETE FROM company_insights
WHERE company_id = @company_id AND batch_date = @batch_date;

INSERT INTO company_insights (company_id, insight_type, severity, title, summary_text, batch_date)
VALUES (@company_id, @insight_type, @severity, @title, @summary_text, @batch_date);
```

## 4. Job 2 — Strategic & Risk Insights Generation

**Output table:** `company_risk_insights`

### 4.1 Purpose

Generate detailed Strategic & Risk Insights for each company. Each insight is a specific, sourced risk or strategic signal with full reasoning fields: Underwriting Relevance, Supporting Evidence, and cited sources. Insights are categorized into four types and power the Strategic & Risk Insights section and detail modal on the Company Detail page.

### 4.2 Four Insight Categories

| Category | Covers |
|----------|--------|
| **Governance & Leadership** | Board changes, executive transitions, auditor tenure, compensation structure, director independence |
| **Risk & Legal** | Litigation, regulatory actions, compliance findings, environmental matters, data security incidents |
| **Event Signals** | 8-K material events, earnings surprises, M&A activity, asset sales, significant contracts |
| **Behavioral Insights** | Management tone, forward guidance credibility, capital allocation philosophy, qualitative signals from earnings calls |

### 4.3 Input Assembly

- **SEC 10-K:** Risk Factors section, MD&A section (full text)
- **SEC 10-Q:** MD&A section, any updated risk disclosures
- **SEC 8-K:** all material event disclosures from the last 90 days
- **SEC DEF 14A:** governance sections (board composition, executive compensation, auditor information)
- **Alpha Vantage news:** all articles from the last 30 days with sentiment scores

**Truncation rule (if total text > 100,000 characters):** prioritize 8-K and DEF 14A in full, then MD&A up to 40,000 chars, then Risk Factors up to 20,000 chars, then news up to 10,000 chars.

### 4.4 Prompt Requirements

- Return **only valid JSON**. No preamble, no markdown fences.
- Return an array of insight objects covering all four categories. **Minimum 2 insights per category** if source material supports it.
- Every insight must **cite the specific source row(s)** it was derived from — use `filing_type`, `section`, and `period_date` to construct the citation label. Use the `url` field from `av_news` for news citations.
- `underwriting_relevance` must explain why this insight matters to an insurance underwriter assessing this company — **not** a general summary of the insight.
- `supporting_evidence` must quote or closely paraphrase the specific text from the source that supports the insight.
- Do not generate insights that cannot be grounded in the provided source text.

### 4.5 Required Output Schema

| Field | Type | Required | Constraints |
|-------|------|----------|-------------|
| `category` | string | Yes | Exactly one of: `Governance & Leadership`, `Risk & Legal`, `Event Signals`, `Behavioral Insights` |
| `risk_type` | string | Yes | Short descriptive label, e.g. `Auditor Continuity`, `CRE Exposure`, `CFO Transition` |
| `severity` | string | Yes | Exactly one of: `high`, `medium`, `low` |
| `title` | string | Yes | Max 80 characters. Specific and factual. |
| `body_text` | string | Yes | 3–5 sentences. Factual, specific, dated. No generic statements. |
| `underwriting_relevance` | string | Yes | 2–3 sentences explaining D&O, E&O, or other underwriting implications. |
| `supporting_evidence` | string | Yes | Direct quote or close paraphrase from source text with filing reference. |
| `source_json` | array | Yes | Array of `{label: string, url: string}`. `url` may be empty string for SEC filings. |

### 4.6 `source_json` Construction Rules

The prompt must instruct SecureGPT to construct source citations as follows:

- **SEC filings:** `label = "{filing_type} {section} ({period_date})"` — e.g. `"10-K Risk Factors (2024-12-31)"`. `url = ""`
- **Alpha Vantage news:** `label = article headline truncated to 60 chars`. `url = url field from av_news`
- Each insight must have **at least one source** in `source_json`

**Example:**
```json
{
  "source_json": [
    { "label": "10-K Risk Factors (2024-12-31)", "url": "" },
    { "label": "Marriott discloses EPA settlement discussions", "url": "https://..." }
  ]
}
```

### 4.7 Validation Rules (before DB write)

- `category` must be exactly one of the four allowed values.
- `severity` must be exactly `high`, `medium`, or `low`.
- `title` ≤ 80 characters, not empty.
- `body_text`, `underwriting_relevance`, `supporting_evidence` — all not empty.
- `source_json` must be a non-empty array with at least one element. Each element must have a non-empty `label` field.
- `source_json` stored as JSON string in DB (`json.dumps()` before insert).
- Insights failing validation are **dropped individually**. Zero-valid-insight companies skipped and logged as `parse_success = 0`.

### 4.8 Output Table — `company_risk_insights`

| Column | Type | Key | Notes |
|--------|------|-----|-------|
| `risk_id` | int identity | PK | Auto-generated |
| `company_id` | int | FK | FK to companies |
| `category` | varchar(100) | | Validated category value |
| `risk_type` | varchar(100) | | From SecureGPT output |
| `severity` | varchar(10) | | `high` / `medium` / `low` — validated |
| `title` | varchar(200) | | From SecureGPT output |
| `body_text` | nvarchar(max) | | From SecureGPT output |
| `underwriting_relevance` | nvarchar(max) | | From SecureGPT output |
| `supporting_evidence` | nvarchar(max) | | From SecureGPT output |
| `source_json` | nvarchar(max) | | JSON string of `[{label, url}]` array |
| `batch_date` | date | | Date of batch run (UTC) |

**Write strategy:**
```sql
DELETE FROM company_risk_insights
WHERE company_id = @company_id AND batch_date = @batch_date;

INSERT INTO company_risk_insights (
  company_id, category, risk_type, severity, title, body_text,
  underwriting_relevance, supporting_evidence, source_json, batch_date
) VALUES (...);
```

## 5. Job 3 — Follow-Up Questions Generation

**Output table:** `company_followup_questions`

### 5.1 Purpose

Generate 12–15 Suggested Follow-Up Questions for Brokers per company. Questions probe the risks and signals identified in Job 2 and help underwriters prepare for broker conversations. Each question includes reasoning fields and source citations that appear in the detail modal.

### 5.2 Dependency on Job 2

Job 3 **must run after Job 2 has completed successfully** for the current `batch_date`. Before calling SecureGPT, Job 3 reads the freshly generated `company_risk_insights` rows for the company and includes them in the prompt context. This ensures questions are directly aligned with the identified risks.

```sql
-- Job 3 prerequisite query
SELECT category, risk_type, severity, title, body_text
FROM company_risk_insights
WHERE company_id = @company_id
  AND batch_date = @batch_date
ORDER BY category, severity
```

### 5.3 Five Question Categories

| Category | Covers |
|----------|--------|
| **Financial** | Capital structure, leverage, liquidity, debt service, refinancing risk |
| **Operational** | Business operations, geographic exposure, franchise performance, conversion pipeline |
| **Market** | Competitive dynamics, macroeconomic factors, industry trends, regional demand |
| **Strategy** | M&A, growth plans, capital allocation, brand strategy, joint ventures |
| **Governance** | Board oversight, executive transitions, auditor matters, compensation alignment |

### 5.4 Input Assembly

- Same SEC and Alpha Vantage source text used in Job 2 (re-queried from Azure SQL — **do not pass Job 2 context between jobs**).
- Additionally: all `company_risk_insights` rows for the company from the current `batch_date` (see 5.2).
- Same truncation rules as Job 2 apply if total text exceeds 100,000 characters.

### 5.5 Prompt Requirements

- Return **only valid JSON**. No preamble, no markdown fences.
- Return an array of **12–15** question objects spanning all five categories. **Minimum 2 questions per category.**
- Each question must be **directly traceable** to a specific risk, filing section, or news item in the source text.
- Questions must be **specific and actionable** — not generic due diligence questions.
- `following_risk` must name the **specific risk** being probed, not a generic category label.
- `underwriting_relevance` must explain the D&O, E&O, or coverage implication relevant to an underwriter.
- `source_json` must cite the specific source(s) that motivated the question, using the same construction rules as Job 2 (Section 4.6).

### 5.6 Required Output Schema

| Field | Type | Required | Constraints |
|-------|------|----------|-------------|
| `category` | string | Yes | Exactly one of: `Financial`, `Operational`, `Market`, `Strategy`, `Governance` |
| `question_text` | string | Yes | The broker question. Specific and factual. **Must end with a question mark.** |
| `summary` | string | Yes | 2–3 sentences of context behind the question — what prompted it. |
| `following_risk` | string | Yes | The specific risk being probed. References a named risk from `company_risk_insights` or source text. |
| `underwriting_relevance` | string | Yes | 2–3 sentences on underwriting or coverage implications. |
| `source_json` | array | Yes | Array of `{label, url}` citing source filings or news articles. |

**Example valid output:**
```json
{
  "questions": [
    {
      "category": "Financial",
      "question_text": "Given total debt rose to approximately $16.5B while cash remains about $0.5B, what is management's target leverage range and refinancing plan over the next 24 months?",
      "summary": "Leverage increased from FY2024 to FY2025 and again in Q1 2026; interest expense rose with higher debt balances.",
      "following_risk": "Debt service capacity and refinancing risk under RevPAR stress",
      "underwriting_relevance": "Q1 2026 total debt $16.5B and cash $0.5B; FY2025 total debt $16.2B; interest expense increased due to higher debt balances.",
      "source_json": [
        { "label": "10-K MD&A (2024-12-31)", "url": "" },
        { "label": "10-Q MD&A (2026-03-31)", "url": "" }
      ]
    }
  ]
}
```

### 5.7 Validation Rules (before DB write)

- `category` must be exactly one of the five allowed values.
- `question_text` must end with a `?` and not be empty.
- `summary`, `following_risk`, `underwriting_relevance` — all not empty.
- `source_json` must be a non-empty array with at least one element.
- Array must contain between 1 and 20 elements.
- Questions failing validation are **dropped individually**.

### 5.8 Output Table — `company_followup_questions`

| Column | Type | Key | Notes |
|--------|------|-----|-------|
| `question_id` | int identity | PK | Auto-generated |
| `company_id` | int | FK | FK to companies |
| `category` | varchar(50) | | Validated category value |
| `question_text` | nvarchar(max) | | From SecureGPT output |
| `summary` | nvarchar(max) | | From SecureGPT output |
| `following_risk` | nvarchar(max) | | From SecureGPT output |
| `underwriting_relevance` | nvarchar(max) | | From SecureGPT output |
| `source_json` | nvarchar(max) | | JSON string of `[{label, url}]` array |
| `batch_date` | date | | Date of batch run (UTC) |

**Write strategy:**
```sql
DELETE FROM company_followup_questions
WHERE company_id = @company_id AND batch_date = @batch_date;

INSERT INTO company_followup_questions (
  company_id, category, question_text, summary,
  following_risk, underwriting_relevance, source_json, batch_date
) VALUES (...);
```

## 6. SecureGPT API Contract

### 6.1 Authentication

- All requests must include the header: `Authorization: Bearer {SECUREGPT_API_KEY}`
- API key read from environment variable `SECUREGPT_API_KEY`. Never hardcoded or logged.

### 6.2 Request Format

```http
POST {SECUREGPT_BASE_URL}/v1/chat/completions
Content-Type: application/json
Authorization: Bearer {SECUREGPT_API_KEY}

{
  "model": "{SECUREGPT_MODEL}",
  "messages": [
    { "role": "system", "content": "<system prompt from versioned template>" },
    { "role": "user",   "content": "<assembled company context>" }
  ],
  "temperature": 0.2,
  "max_tokens": 4000,
  "response_format": { "type": "json_object" }
}
```

`temperature` set to `0.2` for all generation jobs to reduce hallucination and improve output consistency. `max_tokens` set to `4000` — adjust per job if output regularly truncates.

### 6.3 Response Parsing

- Parse `response.choices[0].message.content` as JSON.
- The top-level JSON object must contain a named array field. Each job's prompt must instruct SecureGPT on the exact field name:
  - Job 1: `{ "insights": [...] }`
  - Job 2: `{ "insights": [...] }`
  - Job 3: `{ "questions": [...] }`
- If JSON parsing fails: log `parse_success = 0` in `ai_generation_log`, retry once with the same prompt. If retry also fails, skip company.
- If the array field is missing or empty: treat as parse failure.

### 6.4 Error Handling

| Error | Handling |
|-------|----------|
| HTTP 429 (rate limit) | Wait `Retry-After` seconds from response header, then retry. Max 3 retries. |
| HTTP 500 / 503 | Exponential backoff: 5s → 15s → 45s. Max 3 retries. Skip company if all fail. |
| HTTP 400 | Log request details and skip company. Do not retry — bad request indicates malformed prompt. |
| Timeout | Request timeout set to 60 seconds. Retry once on timeout. Skip on second timeout. |
| JSON parse failure | Retry once with same prompt. Skip company if retry fails. Log `error_message` with first 500 chars of raw response. |

## 7. AI Generation Logging

All three jobs write one row to `ai_generation_log` per company per SecureGPT call, regardless of success or failure.

### 7.1 `ai_generation_log` Table Schema

| Column | Type | Key | Notes |
|--------|------|-----|-------|
| `log_id` | int identity | PK | Auto-generated |
| `run_id` | varchar(50) | | UUID generated at job start — same across all companies in one run |
| `job_name` | varchar(100) | | `key_insights_generation` / `risk_insights_generation` / `followup_questions_generation` |
| `company_id` | int | FK | FK to companies |
| `prompt_version` | varchar(20) | | Version string from prompt template file, e.g. `v1.2` |
| `model` | varchar(100) | | Model name from SecureGPT response |
| `input_tokens` | int | | From `usage.prompt_tokens` in response |
| `output_tokens` | int | | From `usage.completion_tokens` in response |
| `latency_ms` | int | | Wall-clock time of the API call in milliseconds |
| `parse_success` | bit | | `1` if JSON parsed and at least one valid object written, `0` otherwise |
| `error_message` | nvarchar(max) | | Populated when `parse_success = 0`. First 500 chars of error or raw response. |
| `batch_date` | date | | Date of the batch run (UTC) |
| `logged_at` | datetime | | Timestamp of log row insert |

### 7.2 Key Monitoring Queries

```sql
-- Parse failure rate by job and prompt version
SELECT job_name, prompt_version, batch_date,
       COUNT(*) AS total_companies,
       SUM(CAST(parse_success AS int)) AS success_count,
       COUNT(*) - SUM(CAST(parse_success AS int)) AS failure_count
FROM ai_generation_log
GROUP BY job_name, prompt_version, batch_date
ORDER BY batch_date DESC;

-- Average latency per job (last 7 days)
SELECT job_name,
       AVG(latency_ms) AS avg_latency_ms,
       MAX(latency_ms) AS max_latency_ms
FROM ai_generation_log
WHERE batch_date >= DATEADD(day, -7, GETUTCDATE())
GROUP BY job_name;
```

## 8. Acceptance Criteria

### 8.1 Job 1 — Key Insights

- [ ] 8–10 insight cards generated for each company with all required fields populated.
- [ ] `severity` values are exclusively `red`, `yellow`, or `green`. No other values present in DB.
- [ ] `company_insights` rows replaced per company per `batch_date` — no duplicate batch rows.
- [ ] `ai_generation_log` row written for every company processed.
- [ ] End-to-end test with 5 real companies: output reviewed by a domain stakeholder and confirmed factually grounded.

### 8.2 Job 2 — Strategic & Risk Insights

- [ ] Insights generated across all four categories for each company.
- [ ] Every insight contains non-empty `underwriting_relevance`, `supporting_evidence`, and at least one source in `source_json`.
- [ ] `source_json` correctly cites `filing_type`, `section`, and `period_date` for SEC sources.
- [ ] `severity` values are exclusively `high`, `medium`, or `low`.
- [ ] `company_risk_insights` rows replaced per company per `batch_date`.
- [ ] End-to-end test with 5 real companies: `underwriting_relevance` reviewed by an underwriter stakeholder.

### 8.3 Job 3 — Follow-Up Questions

- [ ] 12–15 questions generated per company spanning all five categories.
- [ ] Every `question_text` ends with a question mark.
- [ ] `following_risk` field references a specific named risk — not a generic category label.
- [ ] `source_json` populated for every question.
- [ ] Job 3 reads `company_risk_insights` from the current `batch_date` — confirmed by checking run order.
- [ ] `company_followup_questions` rows replaced per company per `batch_date`.
- [ ] End-to-end test with 5 real companies: questions reviewed by a broker stakeholder for specificity and usefulness.

### 8.4 Shared Acceptance Criteria

- [ ] Parse failure rate < 5% across all companies in first full production run.
- [ ] No API keys or connection strings present in source code or logs.
- [ ] All prompt templates stored as versioned files — version string visible in `ai_generation_log`.
- [ ] Jobs process all active companies and complete within a **2-hour total runtime SLA**.
